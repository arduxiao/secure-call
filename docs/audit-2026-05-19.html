secure-call 安全 / 质量审计报告

审计范围：提交 857d8fa（main 分支）· 审计角度：资深软件安全工程师 · 报告日期：2026-05-19

核心结论：本项目实现了「信令面针对被动监听者的加密」，但宣传语「端对端加密」名不副实—— 信令服务器仍处于可信基（TCB）内。任何能控制信令服务器（包括运维方、CDN、被入侵的服务器）的行为者 都能完整 MITM 双方密钥协商，包括劫持 WebRTC DTLS-SRTP 媒体面。下文按严重度（🔴 严重 / 🟠 高危 / 🟡 中危 / 🟢 代码质量）展开。

🔴 严重：架构性安全声明与实现不符

C1信令服务器是隐含的可信第三方（MITM 可行）

协议本质：

A ──pubKeyA──▶ Server ──pubKeyA──▶ B
A ◀──pubKeyB── Server ◀──pubKeyB── B
双方 ECDH(pubKey对端, secretKey本地) = sharedKey
sharedKey 加密的 SDP/ICE 通过 Server 转发

问题：A 没有任何手段验证「Server 给我的 pubKeyB 真的来自 B」。一个恶意服务器只需：

  • 把 B 的 lookup-room 返回里的 pubKeyA 替换成 pubKey攻击者A
  • 把转给 A 的 peer-joined.pubKeyB 替换成 pubKey攻击者B

服务器同时与 A、B 协商出两条独立的共享密钥，完整地中间人解密/重加密 SDP， 再把自己的 DTLS 指纹塞进 SDP——连后续 WebRTC 媒体面（DTLS-SRTP）也被劫持。

提示：DTLS-SRTP 的安全性靠 SDP 里的 a=fingerprint， 而 SDP 走信令通道、信令通道是服务器在转发——一旦服务器是 MITM，DTLS 的端到端保护就崩塌。 所以不能靠 WebRTC 自身兜底。

C2暗语标志（symbol）解决不了 MITM

代码里把 symbol 写得像身份锚，但它本身是 A 在 create-room 时通过明文发给服务器的。 服务器看得见、存得着、随手能改。

它能挡的：攻击者不知道 A、B 事先线下约好的标志含义时，让 B 不会把电话接给「错的 A」。

它挡不了：

  • 恶意/被入侵的服务器（看得见标志，可原样转发并 MITM 密钥）
  • 对 B 身份的验证——A 这一侧没有任何与 symbol 对应的对端验证机制。 谁先跑赢 race 抢到 join-room，A 就接通了，零确认。

身份验证是单向的、且仅在「服务器诚实」假设下成立——这跟 "端对端" 三个字差得很远。

修复方向（C1 + C2 必须同时做才有意义）

  • SAS 指纹验证：双方 UI 上展示 H(sharedKey) 派生的 4 个 emoji， 两人电话/可信通道里口头核对——攻击者无法同时让 A、B 看到同一指纹。Signal / Telegram / WhatsApp 业界标准做法。
  • 双向暗语：A 选一个，B 也选一个；双方互看是否符合各自的线下约定。 让 A 也有可拒绝的依据。
  • DTLS 指纹绑定：握手时一并交换 DTLS 证书指纹的承诺，再核对实际 SDP 里的 fingerprint。 彻底封死 MITM 改 SDP。

🟠 高危：服务器侧零防御

C3CORS 通配 + 无认证 + 同源部署

server.ts:25:

cors: { origin: '*', methods: ['GET', 'POST'] }

注释里明明写「同源部署，不再用 NEXT_PUBLIC_SOCKET_URL」，CORS 却开成全宇宙。 任何外部页面都能挂到这个信令服务器上跑业务、刷接口、做 DoS。 应锁同源（true 反射 origin 且不带凭据）或显式白名单。

C4无速率限制 / 无输入校验，DoS 表面巨大

signaling.ts 里 create-room、lookup-room、relay-* 都直接信任 client。具体问题：

  • roomId：任意字符串，无长度上限——可塞 1MB 的 key 进 rooms Map
  • symbols：任意字符串、无长度上限
  • pubKeyA / pubKeyB：未校验是否为合法 32 字节 Curve25519 公钥的 base64
  • 每个 socket 可任意多次 create-room，没有 per-socket 配额

Render free tier 512MB，攻击者用一个连接灌几万个房间就把进程打爆。

C5房间码枚举可行

8 位 base32 字母表 ≈ 1012 种，但服务器对 lookup-room 不限频。多连接并发就是分布式爆破：

  • 每次 lookup 都返回 room-info（命中）或 room-not-found（未命中）——这是个明确 oracle
  • 命中后立刻拿到 pubKeyA+symbols，然后赶在合法 B 之前 join-room 抢占 → 合法 B 永远看到 not-found，攻击者直接和 A 通话（A 没有任何 B 身份验证，见 C2）

C6中转载荷无大小上限

relay-offer / relay-answer / relay-ice 完全透传 client 给的 sdp / candidate 字符串。 恶意 peer 可以发 100MB 的 SDP，服务器全量入内存再 emit 给对端——双端瞬间 OOM。 建议硬上限：SDP < 64KB，ICE candidate < 4KB。

🟡 中危

M1断线重连后房间无法恢复

socket.id 是 Socket.IO 临时 ID，断线重连会换。 但 room.socketA / socketB 记的是旧 ID——重连后转发就发到不存在的 socket。 客户端配了 reconnectionAttempts: 10，意图是「自动恢复」，但服务器侧根本接不住， 反而留下僵尸房间。

M2promoteToActive 的 5s 定时器无意义

signaling.ts:57 5 秒后删除 pubKeyA/B/symbols，但通话未必 5s 内能建好， 而且 relay handler 根本不读这些字段——定时器既删不了 race，也没真清除什么风险窗口。

M3useEffect 依赖里塞了不稳定引用

page.tsx 多个 useEffect 把 crypto、setupPeerConnection、resetToHome 列为依赖。useCrypto 每次 render 返回新对象字面量，这些 effect 在每次 render 都重新 attach Socket.IO listener。 正确性上不是 bug，但浪费、且让状态机更难推理。

M4ICE candidate 加密对主动攻击者无意义

现在 SDP/ICE 用 sharedKey 加密。对被动监听信令通道的窃听者有用（不会泄露 LAN IP 和 STUN reflexive 地址）。 但对在信令面的主动攻击者没用——他能直接换 pubKey 拿到 sharedKey（见 C1）。 所以这个加密的实际防御边界要在 UI / 文档里讲清楚。

M5STUN 服务器写死 Google

对一个号称「零痕迹」的项目，硬编 stun.l.google.com 给 Google 送来访探针。 最低限度：再加 Cloudflare、Mozilla 等 STUN，并文档说明。 同时没配 TURN，对称 NAT 后的用户会直接连不通。

M6clipboard.execCommand 回退路径不可见

WaitingScreen 兜底用 document.execCommand('copy') 而把 <textarea> 加入 DOM 时没有定位到屏外，部分浏览器在严苛策略下会因元素不可见而失败。

🛠️ 健壮性 / 运维

  • R1：内存信令 + Render free tier 休眠 ⇒ 重启等于挂电话。生产应至少用持久存储（Redis）或显式声明此限制。
  • R2：信令 handler 未 try/catch，单条 handler 抛错可能让 io 整个挂掉。
  • R3：日志只 console.log，无结构化字段、无 PII 防护规则。
  • R4：测试只覆盖 happy path + 权限被拒 + 改房间号，没有任何针对 MITM / 密钥替换 / 暗语篡改的"攻击者建模"测试。

📌 优先级建议

P0（必修，否则不要叫"端对端加密"）

  1. SAS / emoji 指纹双方人工对码
  2. 服务器输入校验 + per-socket 限频
  3. CORS 锁同源
  4. relay 大小硬上限

P1（快速能做，收益大）

  1. 删 useWebRTC.ts、isInitiator state、allowEIO3、socket 返回
  2. 加 Next.js security headers
  3. 信令载荷类型化（移除 any）
  4. 房间码编辑用生成器同款 alphabet
  5. 双向暗语 / B 侧也有可被验证的身份字段

P2（架构层面）

  1. 状态机 reducer 化
  2. 断线重连协议或显式不重连
  3. 添加对抗性测试（fuzzing 信令、模拟恶意服务器）
