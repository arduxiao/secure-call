secure-call 二次审计报告

审计范围：提交 13be985（main 分支，已应用第一轮 P0+P1） · 审计角度：资深软件安全工程师 · 报告日期：2026-05-19 (round 2) · 前置报告：audit-2026-05-19.html

核心结论：第一轮 P0/P1 大部分真修了——SAS 双向人工对码、服务器输入校验、限频、转发大小硬上限、双向暗语、安全 header、信令载荷类型化都已落地。 但本轮修复过程中引入了一个会让线上立即崩溃的 bug（N1），以及若干新发现的安全弱点（N2–N4）。请优先处理 N1，再做 N2–N4。

🔴 严重：本次修复引入的回归

N1生产环境 CORS 直接锁死，Render 上的部署已经连不上信令

server.ts 引入的 CORS 校验：

const allowedOrigin = process.env.ALLOWED_ORIGIN
if (!origin) return cb(null, true)
if (allowedOrigin && origin === allowedOrigin) return cb(null, true)
if (dev && /^https?:\/\/(localhost|127\.0\.0\.1)(:\d+)?$/.test(origin)) return cb(null, true)
return cb(new Error(`Origin ${origin} not allowed`))

但 render.yaml 里没有 ALLOWED_ORIGIN：

envVars:
  - key: NODE_ENV
    value: production
  - key: PORT
    value: 3000

结果：浏览器从 https://secure-call-kn0h.onrender.com 打开页面， Socket.IO 升级请求带 Origin: https://secure-call-kn0h.onrender.com， 服务器逐条命中失败 → 抛错 → 客户端永远 "正在连接服务器…"。

修法（任选其一，建议都加）：

  • render.yaml 加 ALLOWED_ORIGIN=https://secure-call-kn0h.onrender.com
  • server.ts fallback 到 Render 自动注入的 process.env.RENDER_EXTERNAL_URL
  • 启动时如果 NODE_ENV=production && !ALLOWED_ORIGIN && !RENDER_EXTERNAL_URL 直接 console.warn 或 process.exit(1)，让发布时立刻发现

N2SAS 只有 20 bits，对抗"预计算 + 碰撞"攻击不够

src/lib/sas.ts 用 32-emoji × 4 位置 = 20 bits 熵。对人工实时核对的威胁模型够用， 但对离线预计算模型不够：

  • 攻击者作为 MITM，对方公钥 A、B 是固定值
  • 攻击者磨自己的 secret，使 ECDH(secAtt, pubA) 落在指纹 X
  • 再磨另一个 secret，使 ECDH(secAtt', pubB) 也落在指纹 X
  • 期望 2²⁰ 次 grind 找到一对，普通笔记本 ~30 秒

ZRTP 标准要求 SAS ≥ 16 bits 是基于"攻击者不能重试"的假设。 这里信令是有状态的服务器，攻击者就是它，可以一次性把两侧的 pubKey 同时替换 → 是离线对撞模型。

修法：扩到 6 emoji × 5 bits = 30 bits，或 4 emoji 但用 64-emoji 池 = 24 bits， 或干脆走 PGP 字表风格 4 个英文单词 ≈ 32 bits。前两种 UI 改动最小。

N3限流是 per-socket 不是 per-IP——一行代码绕过

signaling.ts 的令牌桶挂在 WeakMap<Socket, ...>。 攻击者只需 for (let i = 0; i < 1000; i++) io.connect(...) 就有 1000 个独立桶。

CORS 锁同源只挡浏览器 origin，但 curl/Node 客户端没有强制 Origin 头—— 而且 N1 那段 if (!origin) return cb(null, true) 直接放行无 Origin 请求。

修法：用 socket.handshake.address（或 X-Forwarded-For 第一段，Render 走代理）作 key， 桶挂 Map<string, ...> 并在 IP 空闲足够久后清扫。同时收紧 CORS：生产环境拒绝无 Origin。

🟠 高危：仍未根治 或 新发现

N4服务器中转事件没校验发送方角色

if (forwardEvent === 'offer')   target = room.socketB
else if (forwardEvent === 'answer') target = room.socketA
else target = fromA ? room.socketB : room.socketA

服务器只看「转发到哪」，不看「谁发」。后果：

  • B 可以发 relay-offer，服务器照样转给 socketB（即转给 B 自己，自激）
  • B 可以发 relay-answer，服务器转给 socketA → B 可以伪造 A 收到的 answer，搅乱握手
  • 任何能拿到 roomId 的 socket（包括没真正 join-room 的）只要通过了 socketA === socket.id || socketB === socket.id 检查就能发——这个检查已经做了，但 offer/answer 没强制 sender 的具体角色

修法：

if (forwardEvent === 'offer'  && socket.id !== room.socketA) return
if (forwardEvent === 'answer' && socket.id !== room.socketB) return

N5SYMBOL_RE = /^[\p{Any}]{1,64}$/u 太宽

接受任何 Unicode 字符——包括控制字符、RTL 重写、零宽连接符。 客户端只会从 SHAPES/COLORS/COUNTS 的封闭集组合出暗语，服务器侧完全可以收紧到 「只允许这几个 emoji + 空格 + 数字」。当前的宽松规则在客户端被攻陷的场景下会让 verifying 视图渲染奇怪的字符串，可能用于 UI 欺骗。

N6pubKey 正则匹配但未验证解码后字节数 = 32

const PUBKEY_RE = /^[A-Za-z0-9+/]{43}=$/

形式上 44 字符 + 1 个 = padding 对应 32 字节，但服务器没真去 base64 解码并断言长度。 tweetnacl 在客户端会爆错，但服务器的"形式校验"应该深一层：

if (Buffer.from(pubKey, 'base64').length !== 32) return

N7rooms Map 没有全局容量上限

per-socket create 限到 5/30s，但没限「全服务器 rooms 总数」。一万个客户端各创 5 个 = 5 万房间， 每条 ~200 字节就是 ~10MB——Render free tier 512MB 上还撑得住，但完全可以涨到 OOM。

const MAX_ROOMS = 5000
if (rooms.size >= MAX_ROOMS) return socket.emit('error', { message: 'capacity' })

N8限频触发了，但客户端完全不知道

gate() 在拒绝时 socket.emit('rate-limited', ...)， 但 useSignaling 没监听这个事件，UI 没有任何反馈。用户只看到操作"无反应"。 最低限度在客户端 console.warn 一行；理想做法是显示一个 toast 提示。

🟡 中危

N9重连仍然没有恢复协议

socketRef 在 useSignaling 内仍配 reconnectionAttempts: 10， 但服务器 room.socketA/socketB 记的是旧 socket.id——重连后转发去无主 socket， 僵尸房间堆。状态不一致。

N10SAS 视图把 isInitiatorRef.current 当响应式状态读

{isInitiatorRef.current ? '对方已加入' : '已接听'}

ref 在 render 阶段读出来——React 不会因为 ref 变化重新渲染，所以显示文案可能停留在旧值。 当前虽然在切到 connecting 视图前 ref 就稳定了，但这是脆弱的——任何后续重构都可能踩到。 建议同步一个 state 镜像或直接传 prop。

N11peerSymbol 信任服务器原样传过来

B 端在 verifying 视图看到的「对方的暗语」是 joinedSymbol——来自服务器 room-info。 A 端看到的是 symbolsB——来自服务器 peer-joined。任何一处被换都看不出来。

这是双向暗语仍依赖服务器诚实的剩余风险。 SAS 对码是同步独立的（来自双方公钥 ECDH），所以即便 symbol 被换，SAS 还会暴露 MITM—— 但 UI 文案给的暗示是「这两项是独立证据」，技术上 symbol 不是。 文档/UI 需要诚实一点：SAS 是最终防线，symbol 是辅助。

N12CSP（Content-Security-Policy）仍未配

P1.6 加了一堆 header，但 CSP 没动。Next.js dev/prod 用 inline script + style，要靠 nonce 才能套严格 CSP。 建议至少先加：

Content-Security-Policy:
  default-src 'self';
  connect-src 'self' wss: ws:;
  img-src 'self' data:;
  media-src 'self' blob:;
  style-src 'self' 'unsafe-inline';
  script-src 'self' 'unsafe-inline';
  frame-ancestors 'none';

然后渐进收紧到 nonce 化。最大收益：第三方 XSS 注入路径直接堵死。

N13relayBytes 计数器不重置

socketState[socket].relayBytes 一直累加，没在 hangup 时归零。 一个 socket 完成多个连续通话后会被误杀。

🟢 代码质量碎片

  • next.config.ts 的 Permissions-Policy 里 fullscreen=(self) 当前没用到，留着也无害
  • signaling.ts 的 LIMITS 注释里写 verify capacity: 5, refill 1/5s ——1 / 5 在 JS 是 0.2，意思是每秒补 0.2 个 token。 配合 capacity 5，初始可一次性烧 5 个，之后 5 秒补一个。换成 60 / 60 这种「分钟单位」可读性会好
  • next.config.ts 里的 turbopack: {} 空对象可删
  • useSignaling.ts 里返回的 off() 函数没人调（只用 on() 返回的 cleanup）——可以删
  • peer-verify-confirmed 是 void payload，但 protocol.ts 写了 void 类型；客户端 on(...,(payload) => ...) 的 payload 永远 undefined——这块类型推断 OK，只是看起来怪。on('peer-verify-confirmed', () => ...) 更干净

🛠️ 健壮性 / 运维（与第一轮叠加）

  • R5 新发现：本地 e2e 测试在某次跑挂在 SAS 双方都点击 confirm 之后——「连不上 use 流程页或 call 视图」长达 20s 超时。 复现路径推测：dev server HMR 在多轮 page.tsx 重写后累积了陈旧的副作用。 写一份 README 提一句：开发期重大改动后请重启 dev server。CI 用全新进程不受影响。
  • R6：测试只覆盖 happy path 与拒绝场景，没故意发坏数据给服务器看校验是否真生效：超长 roomId、非法 pubKey、跨房间偷转发、超限速等。 这些"对抗性"测试是 P2 的重要组成。
